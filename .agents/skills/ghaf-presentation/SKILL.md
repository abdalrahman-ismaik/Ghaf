# Ghaf presentation

Start with the audience, time available, and observable family moment. Read `PRODUCT.md`,
`DESIGN_DIRECTION.md`, `PROTOTYPE_LIMITATIONS.md`, and the relevant `DEMO_RUNBOOK.md` sequence.
Use current screenshots and the real route/state names before drafting a claim.

Build a short narrative around a Parent and Child making one sustainable action easier: an
approved task, bounded help, the Child's choice, Parent recognition, and permanent symbolic
growth. Give each slide or demo beat one claim and one concrete piece of evidence. Product
screens remain the hero; financial, social, calendar, or location concepts require clear
future/proposed labels until implemented and directly demonstrated.

For two-device scripts, state whether the build actually synchronizes. Separate actual transfer,
manual staging, and prerecorded backup in the rehearsal sheet. Never let edits, duplicated local
fixtures, or timing imply a live connection that has not been observed. Include a short reset and
network-failure recovery beat; do not improvise with real Child information on stage.

Use the repository's approved logos, Alexandria display and Readex Pro body roles, botanical
palette, generous Arabic line height, and equivalent Arabic/English meaning. Express the main
idea with a readable screen, diagram, or short sentence rather than many dashboard statistics.
Use code-native slide or storyboard tooling already available; add a presentation runtime only
if the requested deliverable needs one. Identify any new raster's source and permitted use.

Return the reviewable artifact, timed speaking notes, evidence behind each material claim, and
the exact rehearsal status. Keep named Arabic/cultural review and physical Android evidence
separate from browser inspection. Do not promise a win, developmental outcomes, live AI,
measured environmental impact, or production security without direct support.
